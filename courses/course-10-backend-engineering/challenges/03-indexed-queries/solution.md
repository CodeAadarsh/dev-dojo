# Solution — Indexed Queries

## Step 1 — open the database and observe the bad plan

```bash
sqlite3 ~/.kube-dojo-work/03-indexed-queries/catalog.db
```

```sql
EXPLAIN QUERY PLAN
SELECT p.restricted_notes
FROM products p
JOIN categories c ON p.category_id = c.id
WHERE c.slug = 'classified'
  AND p.is_active = 0;
```

Output (no index):

```
QUERY PLAN
|--SEARCH categories AS c USING INDEX sqlite_autoindex_categories_1 (slug=?)
`--SCAN products AS p
```

`SCAN products` = full table scan on every join. O(n) with n = 5 001 rows here; on a real table with 10 M rows this is catastrophic.

## Step 2 — create the index

```sql
CREATE INDEX idx_products_category ON products(category_id);
```

## Step 3 — confirm the plan changed

```sql
EXPLAIN QUERY PLAN
SELECT p.restricted_notes
FROM products p
JOIN categories c ON p.category_id = c.id
WHERE c.slug = 'classified'
  AND p.is_active = 0;
```

Output (with index):

```
QUERY PLAN
|--SEARCH categories AS c USING INDEX sqlite_autoindex_categories_1 (slug=?)
`--SEARCH products AS p USING INDEX idx_products_category (category_id=?)
```

Both sides are index lookups now.

## Why the index wasn't there

The schema was generated by an ORM migration that created the FK constraint (`category_id INTEGER NOT NULL`) but did not add the companion index. This is the default behaviour of SQLite, MySQL, and PostgreSQL — none of them auto-index foreign key columns. The constraint enforces referential integrity at write time; the index is a separate artefact that accelerates reads.

## Production checklist

- After every `ALTER TABLE ... ADD COLUMN fk_col INTEGER REFERENCES other(id)`, add `CREATE INDEX idx_t_fk_col ON t(fk_col)`.
- Audit your existing schema: `PRAGMA index_list(table_name)` in SQLite; `\d+ table_name` in psql; `SHOW INDEX FROM table_name` in MySQL.
- On a live production table, use `CREATE INDEX CONCURRENTLY` in PostgreSQL to avoid locking. SQLite has no equivalent — a short write-lock is unavoidable.
- Composite indexes: `(category_id, is_active)` would let this specific query do an even tighter index scan (covering both filter columns). Profile before adding composites — they have higher write cost.
