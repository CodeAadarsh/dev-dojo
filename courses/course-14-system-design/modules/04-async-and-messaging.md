# Async, Messaging & Backpressure

> **Module 04 · Course 14** — Synchronous request-response is comfortable but fragile: it chains availability, couples latency, and makes retries the caller's problem. Async messaging decouples those concerns — and introduces a new set of failure modes that are harder to reason about than a 500 status code. This module covers the primitives, the guarantees, and the production patterns that stop async systems from quietly losing data.

You already know that queues exist. This module is about the decisions that separate a queue-slinger from someone who can defend an async design in an interview or an incident review.

---

## Queues vs Streams

Both are message-passing primitives. They answer a different question about **who owns the cursor**.

```
QUEUE (e.g. SQS, RabbitMQ, Celery/Redis)
  Producer ──► [msg] [msg] [msg] ──► Consumer A    ← msg removed after ack
                                ──► Consumer B    ← competing consumers, NOT both get it

STREAM (e.g. Kafka, Kinesis, Redis Streams)
  Producer ──► [offset=1] [offset=2] [offset=3] ──► Consumer Group A (tracks own offset)
                                                ──► Consumer Group B (independent offset)
             messages retained for a configurable window; consumers replay independently
```

The consequential difference:

| | Queue | Stream |
|---|---|---|
| Message durability after consume | Deleted | Retained (by time or size) |
| Multiple independent consumer groups | No — all compete for same messages | Yes — each group has its own offset |
| Replay / reprocessing | Not possible without re-enqueue | Replay from any offset |
| Ordering | Per-queue (not across partitions) | Per-partition |
| Backlog visibility | Depth / queue length | Consumer group lag (per partition) |
| Best for | Task dispatch, job queues | Event sourcing, audit logs, fan-out to N services |

The wrong choice here is a common architecture mistake: using a queue when you need multiple services to react to the same event (fan-out) — every consumer races to consume the same message, and only one wins. Use a stream (or a queue with topic fan-out, like SNS → SQS).

## Pub/Sub

Pub/sub decouples **publishers** (who emit events) from **subscribers** (who consume them) through a **topic** or **exchange**. The publisher does not know who is listening.

```
                        ┌──── Order Service ────► update inventory
Order Placed Event ────►│
(topic: order.placed)   └──── Email Service  ────► send confirmation
                         └─── Analytics     ────► increment counter
```

Two fan-out strategies:

### Fan-out on Write (push model)

When a message is published, the broker **copies it to every subscriber's queue** immediately.

- Reads are cheap (each subscriber pulls from their own queue).
- Writes amplify: 1 event → N copies in storage. For a user with 10 million followers, posting a tweet creates 10 million writes. Twitter's original architecture did exactly this and had to add the celebrity exception (see Module 06).
- Slow / offline consumers do not block fast ones.

### Fan-out on Read (pull model)

One copy stored; each subscriber tracks their own **offset**.

- Write is cheap (1 copy). Kafka uses this model.
- Reads can be expensive for "hot" topics — each consumer reads the same bytes from disk (mitigated by page cache).
- Consumer lag is measurable per group; you can alert on it.

### Consumer Groups

A consumer group is multiple instances of the same logical consumer, each assigned a subset of partitions. Scaling a consumer means adding instances to the group — Kafka rebalances partition assignments automatically. The trade-off: **rebalancing pauses consumption** (brief, but design your commit strategy around it).

```
topic: orders  [partition-0] [partition-1] [partition-2]
                     │               │              │
consumer-group-A:  worker-0       worker-1       worker-0   (2 workers, partition-0 + partition-2 go to worker-0)
```

## Idempotency

An operation is **idempotent** if applying it N times produces the same result as applying it once. In async systems this is non-negotiable: networks drop acks, brokers redeliver, consumers crash mid-process.

### The At-Least-Once Trap

```
Consumer receives message ──► starts processing ──► crashes
Broker never received ack  ──► redelivers message
Consumer starts again      ──► processes it twice
```

If your operation is not idempotent, the second processing is a bug: double charges, double emails, double inventory decrements.

### Idempotency Key Pattern

Every message carries a unique key (generated by the producer, often a UUID or a hash of content-defining fields). The consumer records it in a `processed_messages` table before (or atomically with) the side effect:

```sql
-- atomic: insert key + take the side effect in one transaction
INSERT INTO processed_messages (key, processed_at)
VALUES ($1, now())
ON CONFLICT (key) DO NOTHING
RETURNING id;
-- if no row returned, this was a duplicate — skip the side effect
```

This works because the uniqueness constraint is the guard, and the transaction is the atomicity boundary. The key must be stored in the **same database** as the side effect for the guarantee to hold — storing it in Redis while writing to Postgres introduces a distributed transaction.

### Natural Idempotency

Some operations are naturally idempotent and require no key tracking:
- `SET key = value` (last write wins — only if ordering doesn't matter)
- `INSERT ... ON CONFLICT DO UPDATE` (upsert)
- `UPDATE counter SET count = 5` (absolute set vs `+= 1`)

Design toward natural idempotency first. Idempotency keys are for operations with irreducible side effects (external API calls, emails, bank charges).

## Backpressure

Backpressure is the mechanism by which a **slow consumer signals to a fast producer** to slow down. Without it, the queue grows without bound, memory exhausts, and latency climbs until the consumer dies under its own backlog.

```
Producer: 10k msg/s ──► Queue ──► Consumer: 2k msg/s
                         ↑
                    lag grows 8k msg/s
                    eventually OOM or hours of latency
```

### Pull vs Push

- **Pull** (Kafka, Redis Streams): the consumer fetches at its own pace. Backpressure is implicit — if the consumer stops pulling, the broker just accumulates. You need **lag monitoring** (consumer group lag alert).
- **Push** (HTTP webhooks, some message brokers): the producer sends at whatever rate the broker allows. Backpressure must be **explicit**: HTTP 429, connection-level flow control (TCP), or a bounded buffer that blocks the producer.

### Controlling Ingestion Rate

Techniques in order of preference:

1. **Bound the queue** — reject at the source (return 429 to producers) when depth exceeds a threshold. Forces producers to back off.
2. **Rate-limit producers** — token bucket or leaky bucket at the gateway before messages enter the queue.
3. **Increase consumer parallelism** — add consumer instances. Only effective if the bottleneck is CPU/IO in the consumer, not downstream writes.
4. **Shed load** — for non-critical work, drop messages sampled by priority or age. Never for financial or audit events.

### The Upstream Signal

In HTTP APIs, backpressure is a `429 Too Many Requests` with a `Retry-After` header. In gRPC, `RESOURCE_EXHAUSTED`. In TCP, the receive window shrinks. In Kafka, the consumer simply stops calling `poll()`. All of these are the same idea: the consumer owns the pace.

## Dead-Letter Queues

A DLQ captures messages that **failed processing after N retries** so they don't block the main queue or vanish silently.

```
Main Queue ──► Consumer ──[fails N times]──► DLQ
                                              │
                                    alerting + manual review
                                    or automated reprocessing
```

### Retry Policy

Naive retry (tight loop) turns a transient failure into a thundering herd. The correct policy:

```
attempt 1 → wait 1s
attempt 2 → wait 2s
attempt 3 → wait 4s
attempt 4 → wait 8s + jitter(0–2s)   ← jitter prevents synchronized retry waves
max 5 attempts → DLQ
```

Exponential backoff with full jitter (`sleep = random(0, base * 2^attempt)`) is the standard recommendation from the AWS builders-library.

### Poison Messages

A **poison message** causes the consumer to crash deterministically — not a transient failure, but a bug in processing logic for that specific message shape. Without a DLQ, the broker redelivers it forever and the consumer never makes progress. The DLQ quarantines poison messages so the healthy messages behind them can proceed.

> **DLQ alert rule**: DLQ depth > 0 is a `warning`; DLQ depth growing over 5 minutes is a `critical`. A non-empty DLQ means data your system was supposed to process is sitting unprocessed. Treat it like a 5xx rate spike.

## The Outbox Pattern

The central problem in async systems: you need to write to your database **and** publish an event atomically. They're different systems, so there's no single transaction boundary.

### Why Two-Phase Commit Is Not the Answer

XA transactions across Postgres + Kafka are theoretically possible and operationally terrible: they hold locks across network round trips, Kafka doesn't actually support them well, and a coordinator failure leaves you in a blocked state.

### The Outbox Solution

```
Application Transaction (Postgres):
  ┌─────────────────────────────────────────────────────────┐
  │  INSERT INTO orders (id, ...) VALUES (...)               │
  │  INSERT INTO outbox (id, topic, payload, sent=false)     │  ← same tx
  └─────────────────────────────────────────────────────────┘
                              │
              Outbox Relay (separate process):
                   polls outbox WHERE sent = false
                            │
                   publishes to Kafka/SQS
                            │
                   marks sent = true (or deletes row)
```

Properties:
- **Atomicity**: both the domain write and the outbox write happen in the same Postgres transaction — either both commit or neither does.
- **At-least-once delivery**: the relay publishes and then marks sent. If the relay crashes after publishing but before marking, it re-publishes on restart. Consumers must be idempotent.
- **No lost events**: if the relay is down, events accumulate in the outbox and are published when it recovers. Monitor outbox table depth.

### Variants

- **Polling relay**: simple; adds DB load; fine for moderate throughput.
- **CDC (Change Data Capture)**: Debezium reads Postgres WAL and publishes changes directly to Kafka. Zero polling overhead; operationally heavier.

## Delivery Semantics

| Semantic | What it means | How to achieve it |
|---|---|---|
| At-most-once | Message may be lost; never processed twice | Fire-and-forget; ack before processing |
| At-least-once | Message may be processed multiple times; never lost | Ack only after successful processing |
| Effectively-once | No duplicates from the consumer's perspective | At-least-once + idempotent consumer |
| Exactly-once | True single delivery + processing | Kafka transactions (same cluster only); rarely needed |

The phrase "exactly-once" is often abused in system design interviews. The correct statement: **Kafka 0.11+ supports exactly-once semantics within a single Kafka cluster** using transactions and idempotent producers. The moment you cross a system boundary (write to a database, call an external API), you are back to at-least-once + idempotent consumer.

## Debugging Async Systems

Async bugs are harder than sync bugs because the failure is spatially and temporally separated from its cause. Diagnose by following the message's lifecycle.

| Symptom | Likely cause | Fix |
|---|---|---|
| Consumer group lag growing monotonically | Consumer throughput < producer throughput; or consumer crashed | Check consumer CPU/IO; scale consumers; check for poison message blocking a partition |
| Messages in DLQ with no obvious error | Poison message (schema mismatch, unexpected null, divide-by-zero) | Deserialize and log the raw DLQ payload; add schema validation at the consumer entry point |
| Duplicate side effects despite idempotency keys | Key stored in a different datastore than the side effect (e.g., Redis key + Postgres write — not atomic) | Colocate the key and the side effect in the same transaction |
| Outbox table growing, events not publishing | Relay is down, or relay query missing an index on `WHERE sent = false` | Alert on outbox depth; add index; verify relay process liveness |
| Messages processed out of order, causing state corruption | Assuming ordering across partitions; or consumer parallelism > 1 within same partition key | Route messages with the same entity key to the same partition; use a single goroutine/thread per partition |
| Queue appears empty but consumer is idle | Consumer is polling the wrong queue name (stage vs prod); or message filter/selector excludes all messages | Log the exact queue name at consumer startup; verify environment config |

> **War story.** A payment service at a fintech I consulted for was silently processing refunds twice under load. The idempotency key was stored in Redis with a 5-minute TTL (to "save memory"), and the database write was in Postgres. The key expired before the retried message arrived — so the guard said "new message, process it." The fix was moving the key to a `processed_refunds` Postgres table with a unique index, inside the same transaction as the ledger entry. Redis is cache; Postgres is record of truth. The TTL on the Redis key was the bug, not a feature.

## Common Mistakes

### Unbounded Queues

The classic: no max-size or depth alert, so the queue grows silently during a consumer slowdown. By the time someone notices, there are 48 hours of backlog. Setting `maxReceiveCount` (SQS) or `x-max-length` (RabbitMQ) is not optional — it forces you to decide what to do with excess messages (DLQ, drop, or block the producer) rather than discovering the decision at 2am.

### Duplicate Processing

"We use Kafka, which has exactly-once semantics" — and then the consumer calls an external payment API without an idempotency key. Kafka's transactions stop at Kafka. Any operation outside the cluster requires an idempotency key. Model your idempotency surface as: *for each consumer operation that has an externally visible side effect, there must be an idempotency key stored atomically with that side effect.*

### Ordering Assumptions

"We put everything on the same queue, so it's ordered." Queues are FIFO *in the absence of retries and concurrent consumers*. The moment you have two consumer instances, concurrent delivery to different workers breaks ordering. The moment a message fails and goes to retry-with-backoff, a later message may complete first. Design consumers to tolerate out-of-order delivery, or accept that ordering requires a single consumer and the throughput ceiling that implies.
