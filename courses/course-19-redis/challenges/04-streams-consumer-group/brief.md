# Streams & Consumer Groups

An order-processing service writes every user action to a Redis Stream. Three worker pods share the workload through a single consumer group. During a night deployment, `worker-1` consumed a batch of five events but crashed after acknowledging only four. The unacknowledged entry is stuck in the Pending Entries List — no other worker will pick it up automatically, and the order behind it will never ship unless the on-call engineer understands exactly what happened.

This challenge walks you through building and operating the full pipeline from scratch so you own the mental model before the next incident.

## Prerequisites

- Docker running locally.

`setup.sh` ensures the `dojo-redis` container is running (`redis:7-alpine` on port 6399) and seeds the stream `dojo:events` with exactly five events. It also scaffolds a work file at `~/.kube-dojo-work/04-streams-consumer-group/commands.sh`.

## Background: Redis Streams as a durable message log

Redis Streams, introduced in Redis 5.0, implement an **append-only log** similar in spirit to Apache Kafka but embedded inside Redis. The design centre is a single key that accumulates entries forever — entries are never overwritten or moved; the stream only grows.

```
Key: dojo:events  (type = stream)

  1700000000000-0  event_type=order_placed   order_id=ORD-1001 product=widget-a qty=3
  1700000000001-0  event_type=order_placed   order_id=ORD-1002 product=gadget-b qty=1
  1700000000002-0  event_type=order_shipped  order_id=ORD-1001 carrier=fedex
  1700000000003-0  event_type=order_placed   order_id=ORD-1003 product=widget-a qty=5
  1700000000004-0  event_type=order_cancelled order_id=ORD-1002 reason=out_of_stock

  ID format: <unix-ms>-<sequence>   (auto-generated by Redis when you pass * as the ID)
```

Each entry ID encodes wall time plus a monotonic sequence counter, so the stream is a timeline. `XRANGE dojo:events - +` reads the whole thing in time order; `XRANGE dojo:events 1700000000002-0 +` reads from a specific point forward.

## Consumer groups: at-least-once delivery with shared cursors

A **consumer group** is a server-side cursor that tracks which entries have been delivered (and acknowledged) across a pool of consumers. The same entries are not delivered twice to different consumers in the group. This is the feature that lets you scale horizontally: ten worker pods, one consumer group, each pod pulls its own share.

```
Stream: dojo:events [5 entries]
              │
              ▼
Consumer Group: dojo-workers
  last-delivered-id: 1700000000004-0  ← all 5 have been dispatched

  PEL (Pending Entries List)
  ┌────────────────────────────────────────────────────────────┐
  │ Entry ID            Consumer   Delivered-at   Delivery-cnt │
  │ 1700000000002-0     worker-1   <timestamp>    1            │  ← STUCK, not ACKed
  └────────────────────────────────────────────────────────────┘
```

The **Pending Entries List (PEL)** is the guarantee mechanism. When a consumer reads a message via `XREADGROUP`, the entry moves from the stream's "undelivered" frontier into the PEL — it stays there until the consumer calls `XACK`. If the consumer crashes, the PEL keeps the receipt. A monitoring process can call `XPENDING` to find entries that have been in the PEL too long and use `XCLAIM` to hand them to a healthy consumer.

Compare this to basic `SUBSCRIBE`/`PUBLISH` (Redis pub/sub): a subscriber that crashes while a message is in flight loses that message permanently. Streams give you durability at the cost of requiring explicit acknowledgement.

## The Mission

`setup.sh` seeds `dojo:events` with exactly **five events**. Your task:

1. **Create consumer group `dojo-workers`** on stream `dojo:events`, starting from entry `0` (meaning deliver everything from the beginning of the stream, not just new entries).
2. **Read all five events** as consumer `worker-1` using `XREADGROUP GROUP dojo-workers worker-1 COUNT 10 STREAMS dojo:events ">"`. The special ID `">"` means "give me entries not yet delivered to any consumer in this group."
3. **Acknowledge exactly four of the five entries** with `XACK`. Leave exactly **one entry unacknowledged** in the PEL — any of the five is fine.

`verify.sh` checks three conditions in this order:

| Check | What it inspects | Verifier command |
|-------|-----------------|-----------------|
| Stream non-empty | `dojo:events` exists and has entries | `XLEN dojo:events` |
| Group exists | `dojo-workers` is registered on the stream | `XINFO GROUPS dojo:events` |
| PEL count | **Exactly 1** unacknowledged entry remains | `XPENDING dojo:events dojo-workers` (summary) |

The verifier is strict about the group name (`dojo-workers`) and the consumer name does not matter for the check — any consumer within the group that holds one unacked entry satisfies condition three.

## Key commands reference

```bash
# ── Inspection ────────────────────────────────────────────────────────────────

# List all entries in the stream (get the IDs — you need them for XACK)
docker exec dojo-redis redis-cli XRANGE dojo:events - +

# Count entries
docker exec dojo-redis redis-cli XLEN dojo:events

# Show all consumer groups on a stream (name, last-delivered-id, pending count)
docker exec dojo-redis redis-cli XINFO GROUPS dojo:events

# Show detailed PEL: which entries are pending, for which consumer, since when
docker exec dojo-redis redis-cli XPENDING dojo:events dojo-workers - + 10

# ── Consumer group operations ─────────────────────────────────────────────────

# Create a group starting from the very first entry
#   0  = start-from: deliver entries >= this ID (0 means all history)
#   $  = start-from now (skip existing entries, only deliver new ones)
docker exec dojo-redis redis-cli XGROUP CREATE dojo:events dojo-workers 0

# Read up to 10 undelivered entries as consumer worker-1
#   ">" = special cursor: entries not yet delivered to any consumer in this group
docker exec dojo-redis redis-cli XREADGROUP GROUP dojo-workers worker-1 \
    COUNT 10 STREAMS dojo:events ">"

# Acknowledge 4 entries (substitute real IDs from XPENDING output)
docker exec dojo-redis redis-cli XACK dojo:events dojo-workers \
    <id1> <id2> <id3> <id4>

# ── Cleanup (after the challenge, optional) ───────────────────────────────────
# docker exec dojo-redis redis-cli DEL dojo:events
```

## Why the PEL matters in production

An unmonitored PEL is a silent memory leak. Every unacknowledged entry stores a consumer name, delivery timestamp, and delivery count — that metadata lives in Redis heap alongside your data. A service that `XREADGROUP`s but never `XACK`s will grow the PEL without bound. At Grafana Labs scale (where a stream might ingest 50k events/second), a PEL backlog of a few million entries can add tens of megabytes of overhead before anyone notices.

The operational pattern for production:

1. Monitor `XPENDING` count in your alerting pipeline — alert if count grows above a threshold.
2. Use `XPENDING dojo:events dojo-workers - + 100` (the range form) to find entries idle longer than your SLA.
3. Use `XCLAIM dojo:events dojo-workers healthy-worker <min-idle-ms> <entry-id>` to reassign stale entries to a live consumer.
4. After processing, `XACK` normally.
5. Use `XTRIM dojo:events MAXLEN ~ 1000000` periodically to cap stream length (the `~` allows slight over-trimming for efficiency).
